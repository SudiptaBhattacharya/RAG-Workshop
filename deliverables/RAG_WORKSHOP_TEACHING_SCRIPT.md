# RAG Workshop Teaching Script

| Slide | Slide script | Demonstration script |
|---|---|---|
| 1 · RAG from first principles | RAG retrieves relevant evidence from an external corpus and supplies that evidence to a language model before generation. | `Start here · RAG in one screen`: This demonstration traces one question through loading, chunking, embedding, retrieval, and grounded generation. |
| 2 · What students will build | The objective is to build a minimal RAG pipeline, inspect every intermediate representation, evaluate its failures, and place it within an API and MCP architecture. | `student_lab/rag_starter.py`: The student implementation contains five incomplete functions with explicit inputs, outputs, and success criteria. |
| 3 · The private knowledge problem | A model cannot reliably answer questions about private or recently created documents unless the relevant content is supplied at inference time. | `Experiment 1 · Expose the model's blind spot` → `Run baseline`: The baseline receives the Atlas question without the Atlas memo, so any specific answer lacks document evidence. |
| 4 · RAG in five lines | The minimal pipeline loads pages, creates chunks, embeds chunks, retrieves the nearest evidence, and generates an answer from that evidence. | `Start here · RAG in one screen` → `Run all five stages`: The dashboard executes the same five functions shown on the slide and displays the retrieved evidence and final grounded prompt. |
| 5 · Step 1: load pages with metadata | Loading converts a document into page records while preserving source and page metadata required for later citations. | `Start here` → `load_pages`: The output contains page text, source name, and one-based page number before any chunking occurs. |
| 6 · Step 2: create overlapping chunks | Chunking creates retrievable evidence units, and overlap protects facts that cross a chunk boundary. | `Experiment 3 · Chunking microscope`: Compare size 150 with overlap 0 against size 500 with overlap 100 to observe boundary loss and recovery. |
| 7 · Chunk size changes the evidence | Small chunks improve precision but can remove context, while large chunks preserve context but can dilute the relevant passage. | `Experiment 3` → adjust `Chunk size` and `Overlap`: The same question produces different evidence units because retrieval ranks the chunks created by the current segmentation policy. |
| 8 · Step 3: turn text into vectors | An embedding maps text to a normalized numerical vector so semantic similarity can be estimated with a dot product. | `Experiment 4 · Language becomes geometry`: Paraphrases receive higher cosine similarity than unrelated sentences even when they do not share the same wording. |
| 9 · The corpus becomes a semantic map | The map projects the thirty highest-signal terms into two dimensions, where position represents projected meaning, node size represents frequency, and lines represent similarity or co-occurrence. | `Experiment 4` → keyword network: The visual layout is an approximation for inspection, while retrieval still uses the full embedding dimensions. |
| 10 · Step 4: retrieve the nearest chunks | Retrieval embeds the question with the same model, scores every chunk, sorts the scores, and returns the highest-ranked evidence. | `Experiment 5 · Race keyword search against vector search`: A paraphrased query demonstrates that vector retrieval can rank relevant evidence without requiring an exact keyword match. |
| 11 · Step 5: ground the prompt | A grounded prompt contains the question, retrieved passages, source labels, an evidence-only instruction, and an insufficient-evidence rule. | `Start here` → generated prompt: The prompt is inspected before any model call so retrieval quality and prompt construction remain independently testable. |
| 12 · Same model, different evidence | The comparison changes only the supplied context, which isolates the effect of retrieval on answer accuracy and citation quality. | `Experiment 6 · Run the decisive RAG A/B test` → `Run both conditions`: Condition A has no document context, while condition B receives the retrieved Atlas passage and its source metadata. |
| 13 · Controlled failure experiments | RAG must be evaluated for boundary loss, excessive or insufficient top-k, unanswerable questions, and instructions embedded inside retrieved data. | `Experiment 7 · Break RAG on purpose`: Run each failure condition and classify the defect as parsing, retrieval, generation, data quality, or security. |
| 14 · API, RAG, and MCP | An API transports requests, RAG supplies private evidence, and MCP exposes structured resources or tools to the model. | `Experiment 2` and `Experiment 8`: The API request carries data, the RAG layer selects evidence, and the MCP layer defines permitted resource and tool operations. |
| 15 · The complete architecture relay | The full system retrieves evidence, produces a grounded model decision, prepares a tool call, crosses an API boundary, and stops for human approval before side effects. | `Experiment 9 · Run the complete architecture relay` → `Run the relay`: The interface displays the RAG evidence, grounded synthesis, MCP-shaped arguments, and approval gate as separate stages. |
| 16 · Your build path | Students copy the starter, implement the five functions, test answerable and unanswerable questions, and explain why the highest-ranked chunk was selected. | `student_lab/rag_walkthrough.py` and workshop QR: The first link provides the workshop files, while the optional second link may provide a hosted demonstration without changing the student implementation. |
